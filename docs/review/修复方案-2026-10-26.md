## 1. 阶段 1 — 解析层

### P1 `$$` 公式跨空行配对

**现状**:`lib/markdown/parser.ts` `matchMathOpen`(155-166)只认两种起行:裸 `$$`(multi)与同行闭合 `$$ x $$`(single)。主循环 multi 分支(484-509)从起行向下**无界**搜索裸 `$$` 闭合行。于是 `$$ a+b` 起行、`E=mc^2 $$` 闭合行都不被识别,剩下的裸 `$$` 行跨空行、跨段落与下一段公式的起行配对,中间正文被包进 LATEX。

**修法**(两步,A 必做,B 建议同批做):

- **A · 闭合搜索遇空行即止**。multi 分支的 `while (j < lines.length)` 循环遇到 `lines[j].trim() === ''` 即 `break` → 按「未闭合」回退为文本(既有回退路径,能力面板照常给「未闭合 $$」告警)。
  - 依据:LaTeX 数学模式里空行等于 `\par`,是错误;KaTeX / MathJax 同样不接受。合法公式不含空行,这条边界不会误伤真公式。
  - 原型已验证:只加这一行,现有 738 个测试全过;P1 复现用例变为 `$$ a+b`、`$$`、`正文段落` 三个文本块 + `LATEX "c"`,正文不再被吞。
- **B · 认「带内容的起行 / 闭合行」**(Obsidian / MathJax 常见写法),只放行三种组合,范围仍限同一段落(不跨空行):
  1. 裸起行 + 裸闭合(现状);
  2. 裸起行 + **带内容的闭合行**:`$$\nE=mc^2 $$`——闭合行去尾随空白后以 `$$` 结尾、且不以 `$$` 开头,公式体含该行去掉末尾 `$$` 的部分;
  3. **带内容的起行** + 裸闭合:`$$ a+b\n$$`——起行 `$$` 之后非空、不含 `$$`,公式体含该行去掉开头 `$$` 的部分。
  - **不放行**「带内容起行 + 带内容闭合行」:它正是 `$$100 涨到…\n…200$$` 这类口语双美元的形状,保住既有假阳性防线(`parser.test.ts:763` 一组)。
  - 带内容的起行只在主循环块首、且向下(同段落内)找到裸 `$$` 闭合行时才成立;`isBlockBoundary` **不改**(仍只认 single / multi),段落中间出现的 `$$ a+b` 照旧被段落吸收——与「`$$` 须行首、不轻易打断段落」的口径一致。
  - 公式体拼好后整体 `trim()`,为空则回退(与空公式规则一致)。

**联动检查**:
- `frontmatter.ts:194` 的 L1 规则(`raw.trim() === '$$'` 的 setext 不作标题)保持不变;补一条测试确认 `$$ a+b\n===` 不会被抽为标题(按 B 不构成公式时它是 setext,需确认既有行为是否可接受,写进测试注释)。
- `capability.ts` 的「未闭合 $$」计数只认裸 `$$` 行:A 之后被空行截断的裸起行会如实计入;B 识别出的公式从产出块计 native。无需改。

**测试**(`parser.test.ts`「数学块」组):
- 审查报告两条复现(`$$ a+b\n$$\n\n正文段落\n\n$$\nc\n$$`、`$$\nE=mc^2 $$\n\n正文\n\n$$\ny\n$$`):正文段落保持 unstyled,后一段公式正确成 LATEX;按 B,前一段也成 LATEX。
- 裸起行后遇空行再遇 `$$`:不配对,两行都回落文本,能力面板计 1 条未闭合(注:按 B 若前一行是带内容的,同理)。
- B 三种组合各一例;`$$100 涨到\n下行 200$$`(带内容 × 带内容)保持文本。
- 既有用例全部保持(空公式、围栏内、缩进、`$$100`、A14 同行两段)。

**风险**:有人在 `$$` 块里留空行(LaTeX 本身报错)——A 之后改为原文保留 + 告警,比现状(吞正文)更安全。

**实施记录**:A、B 均已做。check 审查发现 B 初版只以空行为界,`$$100 涨\n- 项\n$$` 会把列表项吞进公式——带内容的起行改为**只看段落续行**(遇 `isBlockBoundary` 或 setext 下划线即止),裸起行仍只以空行为界(公式里 `- b + c` 这类行合法)。残留:独占一行的 `$$100 涨` 紧跟裸 `$$` 会成公式。

### P4 删除首个 H1 导致上下文重拼

**现状**:`h1Handle=remove` 时 `WorkspaceProvider.startImport`(`:649`)先 `stripFirstH1(md)` 在**文本层**删掉标题源行,再对删后的文本 `parseMarkdown`。删行会改变相邻行的关系:首行变 `---` 被当 frontmatter、标题上下两段合并、标题后的段落被吸进前面的列表项。

**备选**:把标题行替换为一个空行而非删除——覆盖了审查里的三个例子,但仍是「改文本再重解析」,空行本身会改变语境(如 `- 项\n# 标题\n  续行` 删后 `  续行` 成为松散列表续段,被吸进列表项)。**不采用**。

**修法(按块去除,构造上精确)**:
1. `parser.ts`:`HeadingVisitor` 增加第 6 个参数 `blockIndex`(两个上报点——ATX `:605`、setext `:676`——都紧跟在 `blocks.push(hb)` 之后,传 `blocks.length - 1`)。新增导出:
   ```ts
   export interface ParsedDoc { blocks: ImportBlock[]; headings: HeadingInfo[] }
   export function parseMarkdownWithHeadings(md: string, opts?: ParseOptions): ParsedDoc
   ```
   内部一次 `parseLines`,同时收集 `onHeading`;`parseMarkdown` 保持原签名(可改为调它取 `.blocks`)。新入口按 P7 惯例走 `withParseOptions`,不残留模块级开关(顺带向优化 O5 靠近)。
2. `frontmatter.ts`:把 `findFirstH1` 的「挑哪个标题当文章标题」抽成纯函数 `pickTitleHeading(headings)`(规则不变:ATX 一级或单行 setext、L1 跳过、纯文本非空),`findFirstH1` / `extractTitle` 改为复用它,判定仍是单一来源。
3. `WorkspaceProvider.startImport`:
   ```ts
   const { blocks: all, headings } = parseMarkdownWithHeadings(md, parseOpts);
   const h1 = pickTitleHeading(headings);
   const extracted = opts.setTitle ? extractTitle(md, parseOpts) : null; // frontmatter 优先,规则不变
   let blocks = extracted?.source === 'h1' && opts.h1Handle === 'remove' && h1
     ? all.filter((_, i) => i !== h1.blockIndex)
     : all;
   ```
   随后的封面首图移除按**块对象**过滤(现有 `findIndex` + `filter` 即可,标题已先移除,不存在下标错位)。
4. 删除 `stripFirstH1`(生产代码仅此一处调用);其单测改写为「`parseMarkdownWithHeadings` + 移除标题块」的等价断言。

**不变量测试**(新增,`frontmatter.test.ts`):
- 审查报告三例:去标题后的块序列 **等于** 原块序列去掉 `blockIndex` 那一块(`# 标题\n---\n作者:张三\n---\n\n正文` → `[DIVIDER, H1 作者:张三, 正文]`;`导语\n# 标题\n正文` → 两段;`- 要点\n# 标题\n正文` → 列表项 + 段落)。
- 语料不变量:对现有测试里的样例文档 + `docs/qa/测试样例-全格式.md`,断言「被移除的块是 header-one 且其纯文本 === extractTitle().title」、其余块与原序列逐一相等。
- 既有 setext / frontmatter 跳过 / 围栏内 `# x` / `$$` 内 `# x` 的标题用例全部保持。

**风险**:`HeadingVisitor` 加参数是向后兼容的(多余实参被旧回调忽略)。`firstTitle`(历史标题)行为不变。

### P5 引用里的代码被改坏

**现状**:`parser.ts:611-616` 引用块逐行剥 `>` 后直接 `walkInline`。引用里的围栏代码每行被当行内文本,`*` / `_` / `` ` `` 被当强调符吃掉。

**修法(本批只做围栏,窄修)**:引用分支剥前缀后的内容若 `matchFenceOpen(content)` 成立,向下收集**连续的引用行**:
- 某行剥前缀后 `matchFenceClose` 成立 → 正常闭合;
- 遇到非引用行(引用结束)仍未闭合 → 按 CommonMark「容器结束即闭合」处理,围栏到引用最后一行为止;
- 内容行剥 `^ {0,3}>\s?`(与现有剥法同一正则)后再按开栏缩进剥前导空白;引用内的空行(`>`)成为代码里的空行。

产出一个 `MARKDOWN` atomic,形状与顶层围栏完全一致:把顶层分支(`:447-468`)里「规范化开栏行 + body + 闭栏行」抽成 `buildFenceMarkdown(openLine, body, closeLine | null, indent)` 共用;容器闭合时 `closeLine` 用开栏 marker 补齐,保证 X 收到闭合的围栏。同时调 `hooks.onFence?.(open, close)`,`forEachContentLine` 的跳过区间随之正确(标题抽取、能力面板扫描不会看到引用代码内部)。

**可见差异**:引用里的代码块会单独成一个代码块,不在引用竖线内——X 的 atomic 块不能嵌进 blockquote,这是平台限制;前后的引用文字仍是 blockquote 块。比现状(代码被改字)安全。

**本批不做**(各自另列,避免一次改动面过大):嵌套引用 `>>`、GitHub alert `> [!NOTE]`、引用内的 `$$` 公式 / 列表 / 标题、把引用内容整体递归解析(会把现在的「每行一个 blockquote 块」变成「每段一个块」,是需要真机看效果的行为变化)。

**测试**:
- 复现用例:代码原样、无 ITALIC、产出 1 个 MARKDOWN atomic,`data.markdown === '```py\ndef f(*args, **kwargs): return a*b*c\n```'`。
- 引用内 `~~~`、带语言 info 的规范化、代码内空行 `>`、容器闭合(引用结束未见闭栏)、引用前后有普通引用文字(前后各成 blockquote 块)。
- 引用内只有开栏、紧接非引用行:按容器闭合成空代码块还是回退文本——定为**回退文本**(body 为空时不产块,与空公式规则同口径)。
- 能力面板:代码块计数 +1,不再出现斜体计数。

### W2 草稿保存的迟到回声被当外部编辑

**现状**:`flushDraft`(`:257-276`)在 `await saveDraft(v)` **之前**就把 `pendingDraft` 置空;onChanged 采纳判定(`:367-370`)只看「`incoming !== mdRef`、无 pending、未在导入」。前一次较慢的写入,其回声晚于下一次 flush 开始到达时,三个条件都满足,被当成另一窗口的编辑采纳。

**修法:自写回声队列**(与 `SettingsProvider` 的 `pendingEchoes` 同思路):
1. 新增纯模块 `lib/storage/echoQueue.ts`:
   ```ts
   createEchoQueue<T>(max: number) → {
     push(v: T): void;      // 发起写入前登记
     consume(v: T): boolean; // 回声到达:命中第 k 项则连同其前各项一并出队,返回 true
     drop(v: T): void;      // 写入失败:该值不会有回声,移除
   }
   ```
   按值比较(`===`)。队列存的是已被 `pendingDraft` / `mdRef` 持有的同一字符串引用,不额外复制;`max = 8`,超出丢最旧。
2. `flushDraft`:`v !== lastPersisted.current` 时才 `draftEchoes.push(v)`(值未变的写入 Chrome 不发 onChanged,登记了会在队列里滞留);成功后 `lastPersisted.current = v`;失败 `draftEchoes.drop(v)`。外部值被采纳时同步 `lastPersisted.current = incoming`。
3. onChanged 草稿分支:**先** `if (draftEchoes.consume(incoming)) → 不采纳`,再走原有的 adoptable 判定(三个条件保留不动,它们防的是另外的场景)。
4. 判定逻辑抽成纯函数 `decideDraftChange({ incoming, current, hasPending, importing, echoes }) → 'echo' | 'adopt' | 'ignore'`,供单测直接驱动竞态时序。

**为什么不改存储格式**(如存 `{ md, writer, seq }`):会牵动 `validateDraft`、备份 / 恢复格式与旧数据兼容,收益只是把同值冲突的理论边角也消掉,不划算。残留边角:本窗口写过的旧值 V 尚在队列中、另一窗口恰好也写入完全相同的 V——被当回声吞掉,但内容相同,无害。

**本批不做**:历史列表的同类竞态(连续两次 `commitHistory` 时前一次回声晚到会短暂回退,随后一次回声到达即自愈,无数据丢失)——记入后续批次,可复用同一 `echoQueue`;Settings / Prefs 迁移到共用 hook 属优化 O4,另做。

**测试**:
- `echoQueue.test.ts`:push / consume 命中第 k 项连同之前出队、未命中返回 false、drop、容量淘汰。
- `decideDraftChange` 竞态时序(审查复现):写 A → 键入 B → flush「AB」→ A 的回声到达 → 判 `echo`(旧实现判 `adopt`,红灯);「AB」回声 → `echo`;另一窗口写 X(无 pending)→ `adopt`;有 pending 时外部写 X → `ignore`(保持现状)。
- 真机 / 手动:两窗口同时开侧边栏,A 窗口编辑后切到 B,B 跟随;单窗口快速连续输入大段文本,无「已从另一窗口同步」误报。
