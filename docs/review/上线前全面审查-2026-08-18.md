> 审查范围：全部源码（桥接链路 / Markdown 解析 / 侧边栏 UI / 存储层 / 图片管道），共约 1.2 万行。

## 总体结论

工程基本面非常好：能力面板「诚实化」的产品哲学、marker 事务、SSRF 纵深防御、设置项置灰而非假开关、真机回归文档——这些都在同类扩展的平均水准之上。但本次审查发现了 **2 条 P0（均在存储层，与「本地优先、数据不丢」的承诺直接冲突）** 和 **12 条 P1**。共性规律很明确，四个模块反复撞上同两类系统性问题：

1. **「第二套实现漂移」**——HANDOFF 里记过两次教训，本次又抓到至少 5 处：Preview 的 frontmatter 剥离、capability 的 `images()` 正则、`firstTitle` vs `extractTitle`、`findFirstH1` 不跳 frontmatter、locateXTab 与 manifest 的子域规则不一致。凡是同一语义存在两套实现的地方，几乎必然已经漂移。
2. **「失败静默 / 假成功」**——存储写失败静默 + 假「已保存」toast、导出备份假成功、复制假成功、ask 模式探测失败无提示、`autoReport=anomaly` 失效。错误路径的可见性是当前最大的系统性缺口。

## P0 — 上线阻断（丢数据风险）

### P0-1 存储写失败全链路静默，手动「保存」失败仍提示成功
`lib/storage/store.ts:23-33` + `lib/workspace/WorkspaceProvider.tsx:185-194,223-226`

- `setItem` 的 chrome 路径 `await chrome.storage.local.set(...)` 不 catch，配额满/存储错误时 reject；所有调用方（草稿 `void saveDraft(v)`、历史 `void saveHistory(next)`、设置/偏好）一律 `void` 丢弃，无 toast、无重试。
- 更糟：`save()` 先 `void saveDraft(md)` 后**无条件** `showToast(t.savedToast)`——写失败也显示「已保存」。
- 触发：配额打满（见 P1-8，完全可达）后用户继续编辑，每次键入的持久化都静默失败；看到「已保存」后关面板/重启浏览器，最近编辑全部丢失。
- 修法：`setItem` 不吞错向上抛；草稿/历史写路径 catch 后展示**持久性**错误条（非 2 秒 toast）+「导出草稿/清理历史」出口；`save()` await 成功后再 toast。

### P0-2 双窗口并发：整体覆盖 last-write-wins，无 `onChanged` 同步
`lib/workspace/WorkspaceProvider.tsx:143,160-164,196-200` + `lib/storage/store.ts:3`

- `md` 与 `history` 都是挂载时一次性快照，全仓无任何 `chrome.storage.onChanged` 订阅；每次写入都是**整份**覆盖。
- 触发：sidePanel 每窗口一个实例。窗口 A 写了半小时草稿，用户回到窗口 B（持陈旧快照）敲一个字符 → B 用陈旧内容整体覆盖 A 的新草稿。历史同理（A 的导入记录被 B 的陈旧数组 commit 抹掉，`historyRef` 只镜像本窗口）。
- 修法：订阅 `onChanged` 回灌 state（最简单策略：非聚焦窗口只读跟随）；或写入带 generation/updatedAt 乐观检查，发现 storage 更新时拒写并提示。

## P1 — 上线前应修

### 桥接与写入链路

**P1-1 覆盖确认弹窗与目标 tab 钉死时序错位——replace 可清掉未经确认的另一篇草稿**
`lib/workspace/WorkspaceProvider.tsx:513-543` + `lib/bridge/importArticle.ts:55`
`writeX` 在 ask 模式下针对**当时**活动标签探测 `hasContent` 并弹确认框，而 `pinnedTabId` 是用户点「覆盖」之后才在 `startImport` 内解析。弹窗挂起期间切到另一篇草稿 B → 点「覆盖」→ 对 B 执行 `blockMap.clear()`，B 的内容从未经过检查即被清掉（X 自动保存还会把清空态持久化）。这是 B1 修复（标题写错文章）的同类竞态在正文通道的复发。
修法：进入 ask 流程前就解析并钉住 tabId，随确认弹窗一起保存透传；或 `startImport` 校验活动 tab 与探测时一致，不一致则中止重新确认。

**P1-2 编辑器定位的「多级 fallback」实为 DOM 顺序，可能误中标题框**
`entrypoints/injector.ts:162-176`
`EDITOR_SELECTOR` 是逗号并集，`querySelectorAll` 按文档顺序返回，书写顺序无优先级；`findEditorElement` 取第一个几何达标（宽>200 高>80）的元素。若 X 标题框（contenteditable、DOM 先于正文）折行两行高度超 80px，会被当成正文编辑器——探针误报三灯，最坏 replace 把整篇写进标题。
修法：拆成有序数组逐级 `querySelectorAll`；显式排除命中标题特征的元素（与 `scoreTitleField` 互斥）。

**P1-3 verify 失败/提交后异常返回 `ok:false`，但内容已写入——用户重试导致重复**
`entrypoints/injector.ts:938-973,1085-1094`
replace 先 `onChange` 提交再 verify；verify 不达标或图片/封面阶段抛异常都返回失败，此时旧内容已清、新内容已（部分）落地。用户看到「写入失败」自然重试：append 整篇重复、图片重复上传。
修法：失败结果增加 `committed: boolean`，提交后失败时 UI 提示「正文可能已写入，请先检查编辑器再重试」。

### Markdown 解析（均经运行时探针确认）

**P1-4 图片 title 未剥离，src 带引号垃圾，上传必败**
`lib/markdown/parser.ts:616-623,664`
`![alt](https://h/a.png "标题")` 实测产出 `source: 'https://h/a.png "标题"'` → 远程 fetch 404 / 本地 vault 查找失败，整图降级。`url "title"` 是 Typora/Pandoc/HTML 转 md 工具的默认输出，高频。
修法：非 `<>` 包裹时剥尾部 `/\s+("[^"]*"|'[^']*'|\([^)]*\))$/`，其余空格保留。

**P1-5 X 官方「复制链接」带 `?s=20` 参数，推文嵌入 100% 漏判**
`lib/markdown/parser.ts:34`
`RE_TWEET` 以 `\/?$` 收尾，带 query 的链接（X 分享按钮默认形态）整行落成 unstyled 死文本（连 LINK 都不是）。另漏 `mobile.twitter.com` 与行尾空格（`parser.ts:337` 用未 trim 的整行匹配）。
修法：`/^https?:\/\/(?:www\.|mobile\.)?(?:x|twitter)\.com\/[^/]+\/status\/(\d+)(?:[/?#]\S*)?$/`，匹配前 `line.trim()`。

**P1-6 标题抽取不跳过 frontmatter，YAML 注释被抽成文章标题**
`lib/markdown/frontmatter.ts:99-127` + `lib/markdown/capability.ts:238-253`
实测 `---\n# 元数据区\n…\n---\n\n# 真标题` → 标题=「元数据区」；`h1Handle=remove` 时还会从 frontmatter **内部**删行。`# 注释` 是合法 YAML 注释（Obsidian 模板常见）。parser 自己有 `frontmatterBodyStart`（`parser.ts:148`）专治此病，但 `forEachContentLine` 的消费方都没用它。
修法：`forEachContentLine`（或各调用方）先用 `frontmatterBodyStart` 跳过文首 frontmatter。

**P1-7 `<>` 包裹的远程图被判 local → host 权限不申请 → 下载必被拒**
`lib/markdown/capability.ts:226-236` + `lib/bridge/imagePermissions.ts:23`
`images()` 用独立正则 `\(([^)]+)\)` 抓 src，`![](<https://h/a b.png>)` 抓到含 `<>` 的串判为 local → `requestRemoteImagePermissions` 不申请该 origin → background 下载被 Chrome 拒。同一正则对 `![a](https://h/f(1).png)` 还会截断 src。AssetsCard 注释明确告诫过「必须用 parseMarkdown 的块级结果而非全文正则」，权限申请这条命脉却仍在用 `images()`。
修法：权限申请改从 `parseMarkdown` 的 ImageBlock 取 src；`images()` 删除或复用 `matchImageLine`。

### 存储与运行环境

**P1-8 未声明 `unlimitedStorage`，历史全文累积可打爆 10MB 配额**
`wxt.config.ts:9` + `lib/settings/options.ts:44,76`
每条历史持久化完整 md 全文，默认上限 200 条还有 `inf` 档；50KB 文档导入 200 次即 10MB。打满后进入 P0-1 的静默失败态（`saveHistory` 整数组重写，已有历史也「冻结」，草稿保存全部失败）。
修法：声明 `unlimitedStorage`（零成本）；同时对单条 md 设体积上限或只存摘要，UI 显示存储占用。

**P1-9 崩溃恢复屏唯一出口是「清空全部本地数据」**
`entrypoints/sidepanel/components/ErrorBoundary.tsx:18-39`
RecoveryScreen 兜住**任意**渲染期异常（包括与数据无关的 UI bug），屏上唯一按钮是 `chrome.storage.local.clear()`——数据完好时按提示操作即全清。
修法：加「先导出备份」按钮（裸读 `storage.local.get(null)` dump JSON，不依赖会崩的模块）；「重置」改为先自动导出再清。

### UI 功能性

**P1-10 设置项 `autoReport=anomaly`（默认值）不生效**
`lib/workspace/WorkspaceProvider.tsx:337`
`setReportVisible(opts.autoReport !== 'never')` 只区分 never/非 never，anomaly 与 always 行为相同；`config.ts:56` 承诺的「仅异常时」是假的。异常数据（deg/imageFail）在同一函数内就有。
修法：`always || (anomaly && (deg > 0 || imageFail > 0))`。

**P1-11 封面「更换」按钮是演示占位，点击弹「演示环境:已模拟操作」**
`entrypoints/sidepanel/components/draft/AssetsCard.tsx:220`
上线产品里出现「演示环境」字样的死按钮。功能未实现就删按钮（封面来源已有文字说明），或实现真实选择。

**P1-12 全局 `outline: none` 摧毁键盘焦点可见性**
`entrypoints/sidepanel/styles/global.css:89-94`
无任何 `:focus-visible` 替代样式，键盘用户完全看不到焦点。删该规则，改 `:focus-visible{outline:2px solid var(--acc);outline-offset:2px}`。

## P2 — 体验缺陷与「UI 撒谎」

### 桥接链路

- **P2-1 后台标签定时器节流导致长导入误报超时**（`injector.ts:275,396-452`）：`waitForNewMedia` 靠 `delay(350)` 轮询、单图 40s wall-clock 预算；隐藏标签 setTimeout 至少 1s 化整、超 5 分钟进 intensive throttling。多图导入切走标签 → 大量图误判 `upload-timeout` 降级，实际可能已上传。修法：MutationObserver 驱动 + 监听 visibility 放大预算，至少 UI 提示「导入期间保持 X 标签前台」。
- **P2-2 marker 清扫删整块，可连带删掉用户导入中途打的字**（`injector.ts:550-592`）：`sweepMarkersOnce` 对含 marker 前缀的块整块 delete，不像 `replaceMarkerWithText` 有非精确保护。用户在占位行内输入过文字、或正文本身含 `__MARKFLOW_IMG_` 字面量（写扩展教程）→ 整块被删。修法：块去掉 marker 后仍有内容时改替换不删块。
- **P2-3 通道超时无取消机制 + postMessage 明文广播的安全面**（`content.ts:196-200,344-353` + `injector.ts:154,1215-1236`）：超时后 injector 仍在后台改写编辑器（`relocateMediaToMarker` 会用陈旧 content 重建 blockMap），可能吃掉用户的手动键入；且 nonce/id/本地图 File 字节全程 window 广播，x.com 上任意脚本可旁听文件字节、伪造 import 指令/结果。修法：握手后换 `MessageChannel` port（页面无法旁听），并给 `runImport` 加 abort 标志。
- **P2-4 子域规则不一致产出永远无效的「请刷新」提示**（`locateXTab.ts:14-15` vs `wxt.config.ts:17-22`）：`isXUrl` 接受任意子域，content matches 只覆盖裸域 → 子域页面被判 `needs-refresh`，刷新永远解决不了。两处统一。
- **P2-5 无跨实例单例守卫**（`injector.ts:151-158,1215`）：双注入（dev 热重载/BFCache 叠加）时两个引擎并发执行同一条 import，交错 onChange 损坏草稿且不可见。`window` 全局标记做单例。
- **P2-6 每次本地图导入后连 persistent「默认文件夹」一并清掉**（`content.ts:329-334,376-398`）：设置页承诺的「默认文件夹（兜底）」每次用后即失效，每篇都要重选重授权——安全缓解的成本全压在核心工作流上。建议只清 active，persistent 保留 handle 靠权限自然回落；或做成默认关的开关。

### 解析与预览一致性

- **P2-7 `- - -` / `* * *` / `___` 三种标准分割线不识别**（`parser.ts:33`）：实测分别产出垃圾列表项（`* * *` 还是单空格+ITALIC 的纯垃圾块）和段落字面量。改 `/^ {0,3}([-*_])( *\1){2,} *$/`。
- **P2-8 块级正则全部要求顶格**（`parser.ts:49-79`）：CommonMark 允许的 0-3 空格缩进标题/引用/围栏全部降级且**前导空格字面量入正文**。统一加 `^ {0,3}`。
- **P2-9 Preview 的 frontmatter 剥离与 parser 双重漂移**（`Preview.tsx:122-129`）：CRLF 文档预览把整个 frontmatter 当正文渲染（parser 实测正确）；无「闭合须在首个空行前」约束。删掉这份第三套实现，复用 `frontmatterBodyStart`。
- **P2-10 预览引擎与 parser 语义系统性不一致**（`Preview.tsx:141-143`）：react-markdown 完整 CommonMark vs parser 子集——裸 URL 预览成链接实际是死文本、行内图片预览渲染实际保留原文、H4-6 预览是标题实际是粗体段落、`- - -` 预览是分割线实际是列表项（预览掩盖了 P2-7）。能力面板花大力气诚实化，预览却按另一套语义许诺。修法：预览改渲染 `parseMarkdown` 的块产出，或至少标注「预览≠X 渲染，以能力面板为准」。
- **P2-11 YAML block scalar / 行内注释产出垃圾标题**（`frontmatter.ts:51-63`）：`title: >` → 标题=`">"`；`title: 我的标题 # 草稿` → 注释入标题。
- **P2-12 `cover: "![[path|alt]]"` 不剥 `|alt`**（`frontmatter.ts:78-79`）：封面查找必败，与 parser 的同语法处理不一致。
- **P2-13 任意数字有序列表可打断段落**（`parser.ts:62,564-567`）：软折行段落中 `2024. ` 开头的行被硬切成列表项且原编号丢弃（X 重编号为 1）。CommonMark 只允许 `1.` 打断段落。
- **P2-14 历史记录标题与实际导入标题不一致**（`capability.ts:238-253`）：`firstTitle` 只认 ATX `# `——frontmatter-only 标题的文档历史显示「未命名草稿」，实际导入标题正确；setext 同样取不到。`firstTitle` 直接调 `extractTitle`。

### 存储与备份

- **P2-15 恢复备份不校验 `kind`/`version`**（`backup.ts:58-62`）：诊断导出文件（恰好带 prefs/options）可被当备份「恢复成功」，用户以为草稿已恢复实际未动。断言 `kind==='backup'` + version 显式分支。
- **P2-16 恢复非原子 + 无确认直接覆盖当前草稿**（`backup.ts:63-69` + `SettingsTab.tsx:178-189`）：`Promise.all` 任一失败时其余已落盘（混合态无提示）；恢复直接覆盖当前草稿无二次确认——比「载入历史」破坏力更大的入口反而没有确认闸门。恢复前弹确认+自动导出当前数据。
- **P2-17 导出备份「假成功」**（`SettingsTab.tsx:15-27,168-175`）：`downloadJson` 内部吞异常，`JSON.stringify` 超限抛 RangeError 时无文件产生但 toast「已导出」——用户凭假备份去点「清除所有数据」是备份功能最危险的失败形态。
- **P2-18 idbRun 事务同步抛时 Promise 永不 settle**（`localVault.ts:42-52`）：坏库状态（upgrade 中断后 store 缺失）下 `db.transaction` 同步抛 → 外层 Promise 悬挂 → 设置页「连接/清除文件夹」按钮永久 pending（`sendFolderRequest` 无超时）。包 try/catch 转 reject + 补 onabort/onerror + 发送侧超时。
- **P2-19 `wipe` 文案与行为不符**（`WorkspaceProvider.tsx:596-599`）：desc 说「删除全部草稿、记录与设置」，实际只清 history+draft，设置与主题保留；与 ErrorBoundary 的全量 clear 也不一致。

### UI 交互

- **P2-20 ask 模式即时探测失败静默 return**（`WorkspaceProvider.tsx:520-522`）：按钮「点了没反应」。补 `showToast(t.errDisconnected)`。
- **P2-21 每次按键整串写 storage 无防抖**（`WorkspaceProvider.tsx:185-194`）：长文档键入卡顿第一嫌疑。300-500ms trailing 防抖 + 卸载 flush。
- **P2-22 AudioContext 泄漏**（`WorkspaceProvider.tsx:202-220`）：每次导入 `new AudioContext()` 从不 close，Chrome 有并存上限，多次导入后音效静默失效。
- **P2-23 预览模式下工具栏仍可点，静默污染文档尾部**（`EditorCard.tsx:63-77`）：textarea 已卸载走兜底分支把 `****` 等拼到全文末尾，预览里看不出来。预览时禁用工具栏。
- **P2-24 拖拽高亮可永久卡住**（`EditorCard.tsx:83-86`）：拖入非文件或读取失败时 `setDragging(false)` 永不执行；dragLeave 滑过子元素闪烁。onDrop 无条件先清 + 补 `reader.onerror` + 计数器。
- **P2-25 报告明细与汇总数据源不一致**（`ReportCard.tsx:54-59`）：导入 await 期间改 md 或切解析开关后，明细按新状态重算、汇总是导入时的旧数据——正是代码注释声称要避免的口径漂移。明细改从 `lastRun.md`+当时 parseOpts 计算。
- **P2-26 历史单条删除无确认无撤销**（`HistoryTab.tsx:124`）：记录可能是文章唯一副本；清空全部有 arm 二次确认，单删反而没有。
- **P2-27 Toast 三连**（`Toast.tsx:39-52`）：错误提示顶着成功绿勾图标；2200ms 固定时长读不完 50+ 字拼接文案（含必读的「文件夹已断开」）；无 `role="status"`。分型换图标 + 时长按文案长度浮动 + aria-live。

## 设计层面：如果重新设计会怎么做

### 1. 解析层：单一事实源（本次审查最大的结构性教训）

手写 parser 为「offset 基于剥标记后文本」选择零依赖自研可以理解，但代价是不断和 CommonMark 长尾打地鼠（本次的 hr 变体/缩进块/图片 title/转义全属此类），且 Preview、`images()`、frontmatter 各自维护平行实现——HANDOFF 记了两次「第二套实现漂移」教训后本次又抓到三处。重设计：**用 micromark/mdast（remark 底层，带位置信息）产出标准 AST，只写一层「AST → ImportBlock」映射器**。CommonMark 正确性外包给业界验证过数万用例的解析器；能力映射、降级决策、offset 计算集中在映射层一处；Preview 渲染同一棵 AST、capability 遍历同一批 ImportBlock、frontmatter 用 AST 的 yaml 节点。四个消费方共享单一事实源后，「预览/计数/权限申请与实际写入不一致」这一整类 bug **在结构上不可能发生**。~30KB 的体积成本远低于信任一致性的维护成本。

### 2. 桥接层：MessageChannel + 进度流 + 事务化

- **MessageChannel 取代 window 广播**：握手时用一次 postMessage 交换 port，此后业务消息（尤其携带本地文件字节的 import）走 port 点对点——页面旁听、nonce 泄露、结果伪造三类问题一次性消失，`createBridge` 的三重匹配也大幅简化。（技术方案 §8 曾以「File 对页面不可隐藏」排除过私有通道，但那挡不住的是 MAIN world 同域内存可见性；port 至少消灭被动旁听与主动伪造，仍值得做。）
- **长任务从请求-响应改为进度流**：import 拆成 `commit → per-image → cover` 阶段事件推送，超时判定从「猜总预算（45s+40s/图）」变为「任一阶段心跳中断」，天然获得取消语义（断流即中止），根治「超时后引擎仍在后台改写」的失控窗口，也顺带解决后台节流误报。
- **写入事务化**：结果带 `committed` 标记，verify 失败明确告知「已写入但未校验」而不是共用 `ok:false`。
- **目标 tab 前移为一等公民**：点「写入」那一刻解析 tabId，作为**必传参数**贯穿确认弹窗/探针/正文/标题全链路，从类型上杜绝「探 A 写 B」——这类竞态已经修过一次（B1）又在覆盖确认上复发，说明靠 review 挡不住，要靠结构挡。

### 3. 存储层：根文档 + 写失败一等公民

「多把散 key 各自整体覆写」换成**带版本号的单根文档** `{schemaVersion, generation, prefs, options, draft, historyIndex}`，历史全文按条独立 key（`markflow:hist:{id}`）——淘汰和配额核算按条进行，写历史不再整数组重写。所有写入走串行队列 + generation 乐观并发检查（storage 比本地新 ⇒ 拒写、onChanged 回灌合并），跨窗口天然一致。**写失败冒泡到全局「持久化健康」状态**：UI 常驻角标 + 重试，而不是 `void` 掉——把「本地优先、数据不丢」从口号变成可被测试钉住的不变量。备份恢复走 staging-then-swap 原子化 + 强制先自动导出。

### 4. UI：从「一堆卡片」收敛为「一条流水线」

当前 Draft tab 纵向堆七层卡片，同一探针结果在 StatusBar 三灯/未连接横幅/PreflightCard 展示三遍，「预检」按钮没有增量价值（不检查文档本身）。重设计：

1. **环境与文档分离**：顶部一个复合状态胶囊（连接 ✓/✗ + 一键修复），预检四行明细收进胶囊展开态，删独立预检按钮与三处冗余。
2. **编辑器成为主角**：`flex:1` 占满剩余高度；素材/能力映射降级为编辑器底部一条摘要 bar（「12 图 · 2 处降级 · 封面:首图」），点击展开抽屉。
3. **写入按钮承担预检职责**：按钮永远告诉你「现在按下去会发生什么」——未连接置灰写明原因、有待授权本地图挂黄点，砍掉一步流程。
4. **报告并入历史**：导入报告就是 History 第一条记录的展开态，Draft tab 只弹 toast+「查看报告」入口。这同时根治 P2-25 的数据源漂移（报告永远从 HistoryItem 渲染），History 从「日志坟场」变成报告的自然归宿。三 tab 分工清晰化为「工作台 / 结果档案 / 偏好」。
5. Settings 的折叠分区+诚实置灰保持现状（做得好），只补三处联动置灰。

## 值得肯定的部分（审查过、确认健康）

- MV3 SW 生命周期设计健康：background 无状态、只做 20s 内代理抓图，不存在休眠丢状态。
