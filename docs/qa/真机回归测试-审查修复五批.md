## 1. 环境准备

### 1.1 构建与加载扩展

```bash
pnpm install && pnpm build   # 项目用 corepack 接管 pnpm,pin 版本自动生效
```

Chrome → `chrome://extensions` → 打开右上角「开发者模式」→「加载已解压的扩展程序」→
选中构建产物目录 `.output/chrome-mv3`。

**每次重新 build 或重新加载扩展后,必须刷新所有已打开的 X 编辑页**(content script 不会
自动替换,不刷新会测到旧代码——典型症状:状态条三灯全绿但写入行为对不上本文档描述)。

### 1.2 账号与页面

- 需要一个**具备 X Premium(可使用 Articles 长文功能)**的账号,已登录。
- 打开 `https://x.com/compose/articles`,新建一篇草稿进入编辑器(URL 形如
  `x.com/compose/articles/edit/<数字>`)。多个用例需要**同时存在两篇不同的草稿**,建议
  提前新建 2~3 篇备用(标题分别标注「测试A」「测试B」便于区分)。

### 1.3 打开侧边栏

点浏览器工具栏的扩展图标(或用已设置的快捷键)打开 Side Panel。确认状态条三灯(页面 /
编辑器 / Draft 实例)全绿——若显示「请刷新此 X 页面以启用插件」,按提示刷新 X 标签页。

### 1.4 构造「双窗口」环境

**Side Panel 在本扩展里是按浏览器窗口(window)划分实例的**(每个窗口一份独立的
WorkspaceProvider 状态,经 `chrome.storage.onChanged` 互相同步,而非按 tab 划分)。构造
步骤:

1. 用 `Ctrl/Cmd+N` 新开一个**浏览器窗口**(不是新标签页)。
2. 在新窗口里也打开一个 X 文章编辑页(可以是同一篇草稿,也可以是另一篇——视具体用例)。
3. 在新窗口里点扩展图标,打开该窗口自己的 Side Panel 实例。
4. 现在两个窗口 = 两个独立的 Side Panel 实例(下文称「窗口 A / 窗口 B」),共享同一份
   `chrome.storage.local`。

### 1.5 构造「同一 tab 内切换文章」(SPA 导航)

部分用例要求**不刷新整页、不换 tab**,只是在 X 编辑器内切到另一篇草稿(单页应用内路由跳
转)。在 X Articles 编辑器里,通常可以通过顶部「返回」箭头 / 草稿列表入口回到文章列表,
再点开另一篇草稿进入编辑——全程 URL 变化但页面不整体刷新(浏览器标签页图标不转圈)。若
你的 X 版本没有直达入口,退而求其次:用编辑器内的浏览器**后退**手势回到列表页(仍是 SPA
内路由,不刷新)、再点开另一篇草稿。

## 3. 测试用例

### T1 · 双窗口同步 · A 编辑 → B 未聚焦自动跟随(P0-2 / B1-2)

前置:窗口 A、B 均已打开 Side Panel,两者草稿区当前**内容相同**(建议先在 A 里「清空」,
两边都是空草稿)。

1. 把窗口 **B 切到后台**(点开窗口 A,让 A 成为当前聚焦窗口;确保 B 不在前台、B 的 Side
   Panel 页面处于 `document.hasFocus() === false` 状态)。
2. 在窗口 **A** 的草稿编辑框里输入一段文字,如「双窗口同步测试 · 来自 A」。
3. 等待 ≥1 秒(草稿写入有 250ms 防抖,足够触发 flush 广播)。
4. 切回窗口 **B**,查看其草稿区内容与是否出现 toast。

**期望结果**:
- 窗口 B 的草稿内容自动变为「双窗口同步测试 · 来自 A」,无需手动刷新或任何操作。
- 窗口 B 出现 toast:**「草稿已从另一窗口同步」**(`draftSynced`)。
- 窗口 B 若原本展示着预检结果/导入报告卡片,此时应一并收起。

### T2 · 双窗口同步 · B 聚焦且有未落盘编辑不被覆盖(P0-2 / B1-2)

前置:承接 T1(两窗口草稿已同步为「双窗口同步测试 · 来自 A」)。

1. 点击窗口 **B**,使其成为当前聚焦窗口。
2. 立刻在 B 的草稿框里继续输入几个字符(如追加「B在打字」),**输入后 250ms 内**(即
   B 本地这次编辑尚未 flush 落盘期间)马上切到窗口 **A**。
3. 在窗口 A 的草稿框里也输入一段不同的文字(如追加「A也在改」),等待其 flush 完成
   (≥1 秒)。
4. 切回窗口 B,检查 B 的草稿内容是否被 A 的值覆盖。

**期望结果**:
- 窗口 B 的本地编辑(「B在打字」)**不会**被 A 广播过来的值吞掉/覆盖——只要 B 在收到
  onChanged 广播时**存在未落盘的本地编辑(pending)**,B 就不采纳外部值。
- B 随后自己的 flush 完成后,会把「B在打字」这版内容写回 storage 并广播;此时窗口 A
  应转而跟随同步为 B 的内容(标准的最后写入方向由谁最后落盘决定,不强求哪一方最终
  获胜,只要**B 打字时不丢字**即为通过)。
- 全程 B 输入框内不应出现光标跳动/内容闪烁/输入被打断的现象。

### T3 · 双窗口同步 · A 清除所有数据 → B 同步清空(P0-2 + P2-19 / B1-2 + B4-4)

前置:窗口 A、B 均有内容(草稿非空,「记录」Tab 至少有 1 条历史——若没有,先在任一窗口
用 `载入示例` 写入一次凑一条历史)。

1. 在窗口 **B** 切到「设置」Tab,展开「07 记录与数据」分区,确认能看到「清除所有数据」
   行,但**先不要点**。
2. 在窗口 **A**,「设置」Tab →「07 记录与数据」→ 点「清除」按钮(此时按钮文案变为
   「确认清除?」),2.6 秒内再点一次以真正触发。
3. 观察窗口 A 的行为,以及切到窗口 B 后的行为。

**期望结果**:
- 窗口 A:清除动作触发后 A 自身会 `location.reload()`,面板重新加载,草稿为空、历史
  为空、主题回默认外观。
- 窗口 B(此前一直开着,未被 reload):其草稿与历史应通过 `chrome.storage.onChanged`
  的 key 删除分支跟随清空(草稿变空、历史列表变空),即使 B 没有手动刷新。
- 主题/设置的清空效果只在**重新读取 storage 后**才生效(reload 或重新打开面板),
  B 若一直没有 reload,主题/设置界面本身可能仍显示旧值属已知边界——但**草稿与历史**
  必须已同步清空(这两者走 onChanged 的运行时监听,不依赖 reload)。

### T4 · 存储写入失败常驻错误条(可选 · 需特殊构造)(P0-1 / B1-1)

> 本用例需要一个**去掉 `unlimitedStorage` 权限的专用测试构建**,标记为可选;若无法
> 构造特殊构建,可跳过并在结果表标 `BLOCKED`,注明原因。

1. 临时编辑 `wxt.config.ts`,从 `manifest.permissions` 里移除 `unlimitedStorage`
   一项,`pnpm build` 得到一份专用测试构建,单独加载为另一个「已解压的扩展程序」
   (与正式构建区分,测完删除)。
2. 打开该测试构建的侧边栏,反复「载入示例」→ 手动追加大量文本 → 保存(或直接在设置
   面板执行几次导入大文档 + 清空历史限制为 `inf`),把 `chrome.storage.local` 写到
   接近或超出默认配额(约 5–10MB,视 Chrome 版本)。也可以直接在该扩展的 DevTools
   Console 里循环写入占位数据撑爆配额:
   ```js
   (async () => {
     const junk = 'x'.repeat(1024 * 1024); // 1MB 占位串
     for (let i = 0; i < 20; i++) {
       try { await chrome.storage.local.set({ [`qa_filler_${i}`]: junk }); }
       catch (e) { console.log('quota hit at', i, e); break; }
     }
   })();
   ```
3. 配额写满后,回到侧边栏草稿框继续编辑内容,触发一次自动 flush(等待 ≥1 秒,或
   手动点「保存」)。

**期望结果**:
- 草稿区顶部出现**常驻**错误提示条(`role="alert"`),文案为存储写入失败提示
  (`storageErrBanner`):「存储写入失败(可能已满)——草稿可能未保存。请导出草稿备份,
  或清理历史记录释放空间。」
- 错误条右侧有「导出当前草稿」按钮(`exportDraftBtn`),点击后应成功下载一个 `.md`
  文件(内容 = 当前草稿的最新文本,含尚未落盘的部分),并弹出成功 toast「草稿已导出」
  (`draftExported`)。
- 手动点「保存」按钮时,若仍处于配额已满状态,应 toast **「保存失败:存储写入出错
  (可能已满)」**(`errStorageWrite`),而不是谎报「草稿已保存」。
- 测完清理:`chrome.storage.local.remove` 清掉 `qa_filler_*` 键,删除临时测试构建。

### T5 · ask 覆盖弹窗挂起期间切文章(P1-1 / B2-1)

前置:设置 Tab →「02 导入行为」→「编辑器已有内容时」选 **「每次询问」**(`onExisting=ask`)。
准备两篇不同的 X 草稿文章 A(用来发起导入)与 B(切换目标)。

#### T5-a · 同一 tab 内 SPA 切换到另一篇文章后点「覆盖」

1. 在 X 文章 **A** 的编辑器里手动打几个字(制造非空内容,触发覆盖询问)。
2. 侧边栏粘贴任意 markdown 草稿 → 点「写入 X 文章」→ 弹出 `OverwriteDialog`
   (「编辑器已有内容」/ `owTitle`)。
3. **不要点任何按钮**,按 1.5 节方法在**同一个 tab** 内切到文章 **B**(SPA 内路由,
   不刷新整页、不换 tab)。
4. 切换完成后,回到侧边栏,点弹窗的**「覆盖」**按钮(`owOverwrite`)。

**期望结果**:
- 弹出 toast:**「目标文章已切换,未写入。请回到原文章或重新点击写入」**
  (`errArticleSwitched`)——**不会**误写进当前 X 页面正在显示的文章 B。
- 切回文章 **A** 检查:A 的正文/标题应保持你在第 1 步手动输入的内容,**不应**出现
  侧边栏刚才粘贴的 markdown 内容(因为目标在弹窗弹出**之前**就已经按 A 的
  `{tabId, articleId}` 钉死,进入 injector 后发现 articleId 不匹配当前 DOM,提交前
  就被拦截,不触碰编辑器)。
- 文章 **B** 的内容应完全不受影响(本来就没打算写 B,也不该被写)。

#### T5-b · 弹窗挂起期间切到另一个浏览器 tab(同窗口内)

1. 重复 T5-a 的第 1、2 步(文章 A 制造冲突、弹出 OverwriteDialog)。
2. 这次**不做 SPA 内切换**,而是在**同一浏览器窗口**里新开一个 tab 或切到已打开的
   另一个普通网页 tab(文章 A 的 tab 仍保留在后台、未关闭)。
3. 切回侧边栏(侧边栏本身与窗口绑定,不随 tab 切换而消失),点弹窗「覆盖」。

**期望结果**:
- 由于目标 tabId 已在弹窗弹出前钉死为文章 A 所在的 tab,写入应**正常成功**,内容落在
  文章 A(即使当前激活的 tab 不是 A)——切回文章 A 的 tab 可看到侧边栏粘贴的内容已
  写入,toast 显示正常的成功文案(`writtenToast` 等)。
- 这与 T5-a 的关键区别:T5-a 是**同一 tab 内**article 变了(articleId 不匹配、写入

  匹配,理应正常写入)。若实测发现 T5-b 也被误判为 `article-switched` 或写入失败,
  记为 FAIL。

#### T5-c · 弹窗挂起期间关闭原 tab

1. 重复 T5-a 的第 1、2 步。
2. 直接**关闭**文章 A 所在的浏览器 tab(不切换,直接关掉)。
3. 点弹窗「覆盖」。

**期望结果**:
